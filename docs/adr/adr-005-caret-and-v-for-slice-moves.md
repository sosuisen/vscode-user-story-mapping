# ADR 005: スライスの移動を `^` と `v` に統一

## Status

Accepted

## Context

本拡張機能では、アウトラインのインデントの深さがスライス（横方向の帯）になる。子のアイテムは、親の1つ下のスライスに置かれる。この既定の配置から外れる書き方が2つある。

- 行末の `+`（ADR 004で言及）。親に付ける。その親の子はすべて、スライスを下がらず、親と同じスライスの1つ下の行に置かれる。
- 本文が `_` だけのアイテム（ADR 003）。親と子の間に挟む。カードを作らず、スライスだけを1つ深くする。

利用者がやりたいことは、どちらも「タスクを上下のスライスへ動かす」ことである。上へ動かすなら `+`、下へ動かすなら `_` と、方向によって書き方が異なる。しかも `+` は親に付け、`_` は子の前に挟む。付ける場所も異なる。同じ目的の操作が2つの文法に分かれているため、覚えにくく、説明も長くなる。

## Decision

スライスの移動を、子のアイテムに付ける1種類のマーカーに統一する。マーカーは本文の先頭に置き、直後に空白を1つ必ず置く。

| 書き方 | 配置 |
| --- | --- |
| `- ^ タスク` | 上に詰める。親と同じスライスの1つ下の行に置く |
| `- タスク` | 既定。親の1つ下のスライスに置く |
| `- v タスク` | 上に1スライスあける。親の2つ下のスライスに置く |
| `- vvv タスク` | 上に3スライスあける。親の4つ下のスライスに置く |

細則は次のとおり。

- `v` の数が、あけるスライスの数である。`^` は繰り返さない。
- マーカーの直後の空白は必須である。`vs codeを開く` のような普通の本文と区別するため。
- GFMのタスクリスト `- [ ]` を崩さない。チェックボックスの後にマーカーを書く。例: `- [ ] ^ タスク`。
- 兄弟ごとに個別に判断する。1つの親の子のうち、`^` の付いた子だけが親のスライスに入る。
- マーカーは列の位置に影響しない。列の決め方（最初の子は親の列、2つ目以降の兄弟は右の列）はこれまでどおり。
- マーカーはカードには表示しない。

行末の `+` と `_` だけのアイテムは廃止する。既存のアウトラインは書き換えが必要になるため、破壊的変更である。READMEと図（`outline-to-map-plus`、`outline-to-map-blank`、文法の例）も書き換える。

## Alternatives

### Alternative 1: `+` と `_` を残す

現状のまま2つの文法を続ける。既存のアウトラインを書き換えずに済む。しかし、同じ目的の操作が方向によって別の文法になる問題は残る。採用しなかった。

### Alternative 2: `+` を子に付ける形に変えるだけ

`+` を親から子へ移し、`_` は残す。付ける場所は揃うが、上下で記号が異なる点は変わらない。`v` の数で距離を表す考え方が `_` の個数と重なり、2通りの書き方が併存する。採用しなかった。

### Alternative 3: 距離を数字で書く

`- +1 タスク` や `- -2 タスク` のように数字で表す。遠くへ動かすときは短く書ける。しかし、`-` はリストマーカーと紛らわしく、`+1` は本文としても自然に現れる。`^` と `v` は矢印として読め、繰り返すだけで距離も表せる。採用しなかった。

## Confidence Level

確信度は高い。利用者の目的が「上下への移動」であることは、既存の2つの文法の使われ方から明らかである。`^` と `v` は矢印として直感的に読める。実装は、親の `+` を見る判定を子のマーカーを見る判定に置き換え、`_` の判定を `v` の数に置き換えるだけである。

次の状況になったら見直す。`^` や `v` で始まる本文がマーカーと衝突する事例が出たとき。横方向の移動にも同様の記法が必要になったとき。

## Consequences

良い結果。スライスの移動が1種類の文法で説明できる。マーカーを付ける場所が子に揃う。距離が `v` の数で読める。

悪い結果。破壊的変更である。既存のアウトラインの `+` と `_` は書き換えが必要になる。READMEと図の更新が要る。

中立的な結果。ADR 003の「`_` を採用」とADR 004で触れた「行末の `+`」は、このADRで置き換えられる。
