# ADR 004: デフォルトのlevel名を空欄にする

## Status

Accepted

## Context

本拡張機能はストーリーマップをMarkdownのアウトラインから描く。アウトラインのインデントの深さがlevel（横方向の帯）になり、帯ごとに背景色が変わる。行末に `+` を付けると、その項目は親項目と同じlevelの1つ下の行（rowInLevel）に置かれる。

Jeff Patton『ユーザーストーリーマッピング』では、マップの一番上の行をアクティビティ、二番目の行をタスクと呼ぶ。この2行を合わせてbackboneと呼ぶ。本拡張機能でもこの呼称に統一する。また、同書ではアクティビティのカードとタスクのカードは色を変えるのが一般的である。

しかし、カードの種類ごとに色を固定するのは、アウトラインを用いた本拡張機能の作図と噛み合わない部分がある。カードで作図するときは、まずタスクを水平に並べ、その後にタスクの上へアクティビティのカードを置く。一方、Markdownのアウトラインは、通常、浅いlevelから順に埋めてゆく。このため、まずタスクを一番浅いlevelに並べる。次にタスクの親項目となるアクティビティを追加する。このときタスクは1段インデントされ、親項目のアクティビティが一番浅いlevelに置かれる。その結果、タスクのカードは最初は一番浅いlevelの色で表示され、アクティビティを追加した瞬間に2番目のlevelの色に変わる。

この色の変化を自然なものにするには、各level（色）の意味を最初からマップ上に表示するのではなく、マップが完成したときに決めるべきである。

現在の実装では、アウトラインに順序付きリストがないとき、上から「1. Backbone」「2. Walking Skeleton」「3. Next Goal」をlevel名として表示している。順序付きリストがあるときは、その項目を上から順にlevel名として使う。

## Decision

デフォルトのlevel名を空欄にする方式を採用する。アウトラインに順序付きリストがないとき、マップの左端にはlevel名を表示しない。level名の列も作らず、帯はマップの左端から始める。帯の背景色はこれまでどおりlevelごとに変える。

順序付きリストがあるときだけ、左端にlevel名の列を作り、その項目を上から順にlevel名として表示する。levelの意味は、マップが形になった時点でユーザーが順序付きリストとして書き込む。

実装では、デフォルトのlevel名の一覧（`Backbone`、`Walking Skeleton`、`Next Goal`）を削除する。READMEのlevel名の説明も「デフォルトでは空欄」に書き換える。

## Alternatives

### Alternative 1: デフォルトのlevel名を表示し続ける

現状のまま、順序付きリストがないときは「Backbone」「Walking Skeleton」「Next Goal」を表示する。初めて使うユーザーにも各levelの意味が伝わり、順序付きリストの書き方を知らなくてもマップの読み方が分かる。しかし、作図の途中で表示される名前が実際の内容とずれる。タスクだけを並べた段階でも一番浅いlevelに「Backbone」と表示され、アクティビティを足すとタスクが「Walking Skeleton」へ移る。名前が先にあると、この移動が誤りのように見える。このため採用しなかった。

### Alternative 2: カードの種類ごとに色を固定する

Jeff Pattonの本に合わせ、アクティビティのカードとタスクのカードを別の色で描く。levelの色とは別に、backboneの中の上の行を青、下の行を緑にする案である。本の見た目に近づく。しかし、Contextに書いたとおり、タスクを1段インデントした瞬間にタスクのカードの色が変わる問題は残る。levelの色とカードの色という2つの色の体系が混在し、説明も複雑になる。このため採用しなかった。

### Alternative 3: level名を設定で変える

デフォルトのlevel名を拡張機能の設定に置き、ユーザーが変えられるようにする。順序付きリストを書かずに名前を変えられる。しかし、level名はマップごとに変わるものであり、設定はすべてのマップに共通である。マップと同じファイルに書く順序付きリストのほうが、マップと名前が一緒に保存されて分かりやすい。このため採用しなかった。

## Confidence Level

確信度は高い。level名の表示は順序付きリストで書く仕組みがすでにあり、デフォルトの一覧を消すだけで済む。変更は小さく、元に戻すのも容易である。マップの読み方は、READMEのサンプルに順序付きリストを含めることで伝えられる。

次の状況になったら見直す。初めて使うユーザーから「levelの意味が分からない」という声が多く出たとき。カードの種類ごとの色分けなど、levelの意味を最初から固定する機能を入れることになったとき。

## Consequences

良い結果。作図の途中でlevel名と内容がずれることがなくなる。タスクを1段インデントしても、名前のない帯の色が変わるだけなので、自然な移動として見える。level名の列がないとき、マップを横に広く使える。デフォルトのlevel名の一覧が消え、実装が少し簡単になる。

悪い結果。順序付きリストを書かないと、level名がまったく表示されない。初めて使うユーザーには各levelの意味が伝わりにくい。READMEのサンプルと図に順序付きリストを含めて補う必要がある。順序付きリストを書き足した瞬間に左端の列が現れ、マップ全体が右へ動く。

中立的な結果。levelの意味を決めるのはユーザーの役割になる。「Backbone」「Walking Skeleton」といった名前は拡張機能の語彙ではなく、READMEで紹介する推奨例になる。
