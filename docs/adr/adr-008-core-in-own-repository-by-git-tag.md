# ADR 008: コアを独立したリポジトリに移しGitのタグで参照する

## Status

Accepted

Amended by ADR 009（コアの参照の方法。Gitのタグではなく、crates.ioの版で参照する。クレート名も`storymap`に変わった）

## Context

ADR 007で、コアをRustのライブラリにした。そのとき、`story-map-core`と`story-map-wasm`の2つのクレートを、拡張機能のリポジトリのCargoワークスペースに置いた。

`story-map-core`は、拡張機能の外で使うためのクレートである。中心はRustで、ほかの言語からもRustのライブラリを包んで使う。しかし、拡張機能のリポジトリの中にあると、使う側は拡張機能のリポジトリ全体に依存することになる。コアの版も、拡張機能の版と分けて管理できない。また、コアのテストと拡張機能のテストが、1つのリポジトリに混ざる。

一方で、拡張機能は、これまでどおりどのマシンでもビルドできなければならない。特定のフォルダ構成でしかビルドできない形は避けたい。`story-map-wasm`は、拡張機能専用のバインディングであり、公開しない（`publish = false`）。

## Decision

`story-map-core`を、独立したリポジトリ（`sosuisen/story-map-core`）に移す。拡張機能は、このクレートをGitのタグで参照する。

新しいリポジトリには、1つのクレートだけを置く。ワークスペースにはしない。コアのソース、テスト、READMEは、このリポジトリで管理する。READMEのコード例は、doctestとして実行する。

`story-map-wasm`は、拡張機能のリポジトリに残す。依存は`git = "https://github.com/sosuisen/story-map-core", tag = "v0.1.0"`のように書く。`Cargo.lock`が、タグの指すコミットを固定する。

コアの版は、story-map-coreのリポジトリのタグで決める。拡張機能で新しい版を使うときは、先にコアで新しいタグをpushし、そのあと`story-map-wasm/Cargo.toml`の`tag`を書き換える。

## Alternatives

### Alternative 1: 拡張機能のリポジトリに残す

1つのリポジトリで、コアと拡張機能を同時に変えられる。しかし、コアを使う側は、拡張機能のリポジトリ全体に依存することになる。コアの版も、拡張機能と分けられない。コアを広く使えるようにする目的に合わないため、採用しなかった。

### Alternative 2: ローカルのパスで参照する

`path = "../../../../RustProject/story-map-core"`のように書く。コアを変えると、すぐに拡張機能へ反映される。しかし、このマシンと同じフォルダ構成でしかビルドできない。CIでもビルドできないため、採用しなかった。

### Alternative 3: crates.ioに公開して、版で参照する

Rustでは最も一般的な形で、使う側も依存を書きやすい。しかし、crates.ioへの公開は取り消せない。APIがまだ固まっていないので、今は早いと判断した。APIが固まったら、公開を検討する。

### Alternative 4: Gitのブランチやコミットで参照する

`branch = "main"`や`rev = "..."`と書く。ブランチで参照すると、`cargo update`のたびに中身が変わりうる。コミットで参照すると、どの版かが人に読めない。タグなら、版が読めて、中身も変わらない。

## Confidence Level

確信度は高い。移したあとも、拡張機能のテスト133件はすべて通った。旧実装との出力比較でも、差はなかった。`Cargo.lock`が、タグ`v0.1.0`のコミットを指していることも確かめた。story-map-core側でも、テスト22件とclippyが通った。

次の状況になったら見直す。

- コアのAPIが固まったとき。crates.ioへの公開を検討する。
- コアと拡張機能を同時に変えることが多くなり、タグを打つ手間が開発の妨げになったとき。
- GitHubのリポジトリを移す、または名前を変えるとき。依存のURLを書き換える必要がある。

## Consequences

良い結果。Rustのアプリは、拡張機能のリポジトリに依存せずにコアを使える。コアの版を、拡張機能の版と分けて管理できる。コアのテストとREADMEが1か所にまとまり、READMEのコード例もdoctestで確かめられる。拡張機能は、どのマシンでもCIでも、これまでどおりビルドできる。

悪い結果。コアと拡張機能を同時に変えるときの手間が増えた。先にコアを変えてタグをpushし、そのあと拡張機能の`tag`を書き換える必要がある。拡張機能のビルドには、GitHubへのネットワーク接続が要る。ただし、一度取得すれば、Cargoのキャッシュから使える。

中立的な結果。ADR 007の「Cargoのワークスペースに2つのクレートを置く」は、このADRで置き換わる。コアをRustで書き、WebAssemblyで呼ぶという決定そのものは変わらない。拡張機能のリポジトリでは、`cargo test`で実行するRustのテストがなくなった。コアのテストは、story-map-coreのリポジトリで実行する。
