# ADR 001: ObsidianプラグインではなくVSCode拡張機能として開発する

## Status

Accepted

## Context

「User Story Mapping」は、アウトラインとして書いたユーザーストーリーマップをマップ表示で眺められるようにするプロダクトである。当初はObsidianのコミュニティプラグインとして開発を始め、プラグインの骨格を作ってテストVaultにロードするところまで完了していた。

Obsidianを選んだ当初の理由は、KCGのプロジェクト演習でノートツールとしてObsidianを使ってもらう想定だったからである。しかし、開発者の久保田自身は日常的にObsidianを使っていない。また、学生は演習でVSCodeも使うため、プロダクトの動作環境をVSCodeにしても演習の前提は崩れない。

本プロダクトは「書き慣れたアウトラインを編集するだけでマップができる」ことをコンセプトとするため、快適なアウトライン編集が動作環境に求められる。VSCodeでも、Markdown All in One拡張機能をインストールし、キーバインディングをアウトライナー風に変更することで、アウトライン編集が十分にできることを確認した。

## Decision

VSCodeの拡張機能として開発する方式を採用する。Obsidianプラグイン版の開発は中断する。

アウトライン編集はVSCode本体とMarkdown All in One拡張機能に任せ、本拡張機能はマップ表示のプレビューを提供する。

## Alternatives

### Alternative 1: Obsidianプラグインとして開発を続ける

骨格の実装とテストVault環境がすでにあり、そのまま進められる。Obsidianはアウトライナーとしての編集体験も良い。しかし、開発者自身が日常的に使わないツールでは、ドッグフーディングができず、利用者としての改善の気づきが得られない。演習でもObsidianの導入・習得を学生に求めることになる。このため採用しなかった。

### Alternative 2: コアを共通化してObsidianとVSCodeの両方に対応する

マップ描画のコアを共通ライブラリとし、両プラットフォームのアダプタを作る。将来の選択肢は広がるが、個人開発の規模に対して構成が複雑になりすぎる。まだ1つ目の画面もできていない段階での抽象化は早すぎる。このため採用しなかった。

## Confidence Level

確信度は高い。開発者自身が日常的に使う環境で作るという判断は、個人開発の継続性に直結する。アウトライン編集がVSCodeで十分にできることも確認済みである。Obsidian版で得た知見（PRD、ストーリーマップ、Vault分離の考え方）はほぼそのまま流用できるため、切り替えのコストも小さい。

次の状況になったら見直す。演習や利用者からObsidian版の需要が強く出たとき。VSCode側のMarkdownアウトライン編集に重大な制約が見つかったとき。

## Consequences

良い結果。開発者が日常環境でドッグフーディングしながら開発できる。学生は使い慣れたVSCodeでそのまま利用できる。アウトライン編集の実装をVSCode本体とMarkdown All in One拡張に任せられるため、本拡張機能はマップ表示に集中できる。

悪い結果。Obsidian版で作った骨格・テストVault環境・ADR 001（Vault分離とジャンクション）は使わなくなる。PRDの1節（概要・背景・対象ユーザー）と2節、ストーリーマップの一部（プラグインの準備など）をVSCode向けに書き直す必要がある。快適なアウトライン編集にはMarkdown All in One拡張機能のインストールとキーバインディングの変更という利用者側のセットアップが必要になる。

中立的な結果。開発ワークフロー（PRD → ストーリーマップ → TDD）は変わらず継続する。配布はVSCode Marketplaceまたは.vsixファイルとなり、非機能要件の配布方法も更新が必要になる。
