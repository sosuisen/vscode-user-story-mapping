# ADR 009: コアをcrates.ioの版で参照する

## Status

Accepted

## Context

ADR 008で、コアを独立したリポジトリに移し、拡張機能からはGitのタグで参照すると決めた。そのとき、crates.ioへの公開は見送った。公開は取り消せず、APIがまだ固まっていなかったためである。ADR 008は、APIが固まったら公開を検討するとしていた。

その後、コアに画像出力（`image` feature）を加えた。クレートの名前も`story-map-core`から`storymap`に変えた。「core」という名前は、拡張機能の中核部品という意味に読め、独立したライブラリの名前に合わなくなったためである。GitHubのリポジトリも`sosuisen/storymap`に変えた。名前を変えたことで、ADR 008が見直しの条件に挙げた「リポジトリの名前を変えるとき」にも当たった。

そして、`storymap` 0.2.1をcrates.ioに公開した。Rustの開発者は、GitのURLを書かなくても、版だけでコアを使えるようになった。一方、拡張機能は、まだGitのタグでコアを参照している。同じクレートを、公開した側と拡張機能とで別の経路から取ることになる。

## Decision

拡張機能は、コアをcrates.ioの版で参照する。`story-map-wasm`の依存は、`storymap = { version = "0.2.1", features = ["html"] }`のように書く。`Cargo.lock`が、使う版を固定する。

コアの版を決めて公開する作業は、storymapのリポジトリで行う。手順は次のとおりである。まず`Cargo.toml`の`version`を上げて`main`にマージする。次に同じ版のタグを打ち、`cargo publish`で公開する。拡張機能で新しい版を使うときは、公開のあとで`story-map-wasm/Cargo.toml`の`version`を書き換える。

コアを別のリポジトリに置き、`story-map-wasm`を拡張機能のリポジトリに残す点は、ADR 008のまま変えない。

## Alternatives

### Alternative 1: Gitのタグで参照し続ける

ADR 008のままにする。拡張機能の依存を変える手間はない。しかし、公開した版と拡張機能とで、同じクレートを別の経路から取ることになる。タグとcrates.ioの版が食い違っても気づきにくい。拡張機能も、ほかの利用者と同じ形でコアを使うほうがよいため、採用しなかった。

### Alternative 2: ローカルのパスで参照する

ADR 008のAlternative 2と同じである。コアの変更がすぐに反映される。しかし、このマシンと同じフォルダ構成でしかビルドできず、CIでもビルドできない。ADR 008と同じ理由で、採用しなかった。

## Confidence Level

確信度は高い。依存をcrates.ioの版に変えたあとも、拡張機能のテスト133件はすべて通った。`Cargo.lock`が、crates.ioの`storymap` 0.2.1を指していることも確かめた。

次の状況になったら見直す。

- コアと拡張機能を同時に変えることが多くなり、公開の手間が開発の妨げになったとき。公開した版は取り消せないので、試しの版を出しにくい。
- コアの公開を止める、またはcrates.ioから別の名前に移すとき。

## Consequences

良い結果。拡張機能は、ほかのRustの利用者と同じ形でコアを使う。そのため、公開した版の問題に、拡張機能の開発でも気づける。依存の書き方は版だけになり、GitのURLとタグは要らなくなった。ビルドもcrates.ioから取るので、GitHubへの接続は要らない。

悪い結果。コアと拡張機能を同時に変えるときの手間は、ADR 008より増えた。コアの変更を拡張機能で使うには、crates.ioへの公開が要る。公開した版は削除も差し替えもできない。そのため、試しの版を気軽に出せない。

中立的な結果。ADR 008の「Gitのタグで参照する」は、このADRで置き換わる。コアを別のリポジトリに置くという決定は変わらない。storymapのタグは、公開した版の記録として、これからも打つ。
