# ADR 002: マップ描画にHTML/CSSを採用

## Status

Accepted

## Context

Webviewパネルの中にユーザーストーリーマップを描画する方式を決める必要がある。PRDの要件は、配置の自動整列、編集から反映まで体感で即時、規模は数十〜百枚程度のカード、将来はズーム・横軸ストーリーごとの色分け・完了チェックの表示である。マップ表示上での直接編集はNon-goalである。また、ユーザータスクとして「ストーリーマップをPNGで保存する」が追加された。

候補は、素のHTML/CSS、React等のUIフレームワーク、Canvas（参考としてSVG）である。テストフレームワークはMocha単独の方針が決まっている。

VSCodeのWebviewはサンドボックス化されており、どの方式でも、保存機能は「Webview内で画像データを生成し、postMessageで拡張機能側へ送り、拡張機能がファイルに書く」という共通の配線になる。

## Decision

素のHTML/CSSで描画する方式を採用する。

マップの本質は「列（アクティビティ）×行（重要度）」の格子配置であり、CSS Gridの自動整列をそのまま使う。マップの配色は設定由来の独自配色とし、テーマへの追従はしない。

HTML生成は「マップのモデル → HTML文字列」の純関数として実装する。これにより、Webviewを起動しない高速なユニットテストをMochaで書ける。更新は全再生成方式から始める。百枚規模なら体感即時の要件を満たせる。

## Alternatives

### Alternative 1: React等のUIフレームワーク

差分描画が得意で、状態が複雑なUIに向く。しかし、Webview内アプリとして2つ目のビルドターゲットが必要になり構成が増える。コンポーネントテストにはjsdom等が必要で、Mocha単独の方針と摩擦がある。マップは読み取り専用（直接編集はNon-goal）で状態管理の出番が少なく、百枚規模では全再生成でも十分速いため、現時点ではオーバーキルと判断した。状態が複雑化したら移行を再検討する。

### Alternative 2: Canvas

自由描画とピクセル制御に強い。しかし、テキストの折返し・自動整列・テーマ連携・アクセシビリティをすべて自前実装することになり、CSS Gridが無償で提供するものを捨てる形になる。描画結果がピクセルのため、テストで検証できるものがほぼない。数千枚規模の性能が必要になったときの選択肢であり、現在の規模では不要。

### Alternative 3: SVG

ベクターのまま `.svg` 保存でき、`svg2pdf.js` で真のベクターPDFも作れるため、書き出し能力は最も高い。しかし、テキスト折返しや自動整列のレイアウトコストがHTML/CSSより高い。保存要件はPNGで足りることが確認できたため採用しなかった。将来ベクター出力が要件になった場合は、画面表示はHTML/CSSのまま、書き出し時だけマップモデルからSVGを別生成する折衷案がある。

## Confidence Level

確信度は高い。自動整列はCSS Gridの本業であり、規模要件（数十〜百枚）に対して性能面の不安もない。ビルド構成とテスト方針を変えずに済み、PNG保存も `html-to-image` 等の追加で実現できることを確認済みである。

次の状況になったら見直す。ベクターPDFや大判印刷が要件になったとき（SVG書き出し器の追加を検討）。マップ上の直接編集がNon-goalsから外れたとき（Reactへの移行を検討）。カードが数千枚規模になり全再生成では間に合わなくなったとき。

## Consequences

良い結果。ビルド構成は現状のまま増えない。HTML生成が純関数なので、WebviewなしでMochaの高速なユニットテストが書ける。PNG保存は `html-to-image` の追加で実現できる。

悪い結果。ベクターPDFが必要になった場合は、SVG書き出し器の追加実装が必要になる。差分描画ではないため、将来カード数が桁違いに増えたときは方式の見直しが要る。

中立的な結果。更新は全再生成方式から始める。Webview内のJavaScriptは当面最小限（将来のズーム・保存機能で増える）。
